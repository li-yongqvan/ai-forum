# issue #74 deploy 静默回退防护决策记录

> 日期：2026-08-28 立项；D1/D2 于 2026-08-31 用户访谈补定（本票设计阶段）
> 背景：issue #74「deploy 后自动核对『新代码在跑』防静默回退」——部署完成后自动核对 api 镜像 ID + `schema_migrations`，不匹配则本次 deploy 标 FAIL（CI 红），不再静默绿。
> 关联：设计文档 `docs/plans/74-deploy-verify-设计文档.md`、评审意见书 `docs/plans/74-deploy-verify-设计文档-评审意见书.md`（有条件通过，条件已采纳）。

## 已确认决策

### D1：核对失败时前端换装的处理 —— 跳过换装，整站停旧码
- **决策**：部署核对失败（检测到 api 已回退到旧镜像 / 迁移缺失）时，**立即 exit 1 并跳过前端换装与 nginx reload**；站点整体停留在「旧前端 + 旧 api」（版本自洽、可用性优先），本次 deploy 标 FAIL（CI 红）。
- **问题与选项**：a) 跳过换装整站停旧码（推荐）；b) 仍换装新前端再标红（会造成「新前端 + 旧 api」接口错配）。
- **理由**：handoff §二 明确警示「新前端 + 旧 api」版本错配隐患；整体停旧码 = 版本自洽、站点可用性优先。deploy 红与站点健康可并存（文案区分「deploy 失败但站点健康停旧码」vs「站点也挂了」）。
- **弃选**：仍换装新前端（制造错配态）；核对失败仅 WARN 不退出（回到静默盲区）。
- **确认**：用户确认（2026-08-31）。

### D2：scp 应急模式的覆盖 —— 抽共享脚本，双模式都核
- **决策**：新建 `deploy/verify-deployed.sh` 共享核对脚本，server 模式（`deploy-server.sh` 内置）与 scp 应急模式（`deploy.yml` 内联）**都调用**。
- **问题与选项**：a) 抽共享脚本两模式都核（推荐）；b) 只做 server 模式、scp 留注记。
- **理由**：scp 应急路径当前无迁移核对（§2.3）；成本低（一脚本 + deploy.yml 一行）；应急路径同样需要「新代码在跑」保证。
- **弃选**：只做 server 模式（应急路径迁移缺失照样不会红）。
- **确认**：用户确认（2026-08-31）。

### D3：核对位置 —— 方案 A（deploy-server.sh 内置 + 共享脚本），方案 B 不做
- **决策**：采用方案 A：核对逻辑内置进部署脚本（server 模式 `deploy-server.sh` + scp 模式内联），经共享 `verify-deployed.sh` 实现；不做 CI 独立 check job（方案 B）。
- **理由**：A 天然覆盖两种 DEPLOY_MODE；核对就在回退逻辑旁边，时序直观；非零退出经 ssh-action 步（`set -euo pipefail`）自动红 CI，零 CI 层改动。
- **弃选**：方案 B（CI 独立 check job 部署后 SSH 查服务器）——重复造轮子、多一跳 SSH、时序分离更易出错，无法比 A 提供更多保证。
- **确认**：handoff 推荐 + 用户（2026-08-28 立项时采纳）。

### D4：不做自动修复 / 自动重试
- **决策**：本次只做检测 + 标 FAIL；不做自动修复/自动重试。
- **理由**：issue #74 目标原文「不匹配则本次 deploy 标记 FAIL」；修复是后续开放项。
- **确认**：handoff §二「明确不做」+ issue #74 原文。

### D5：不动既有迁移文件
- **决策**：不动 `backend/migrations/` 任何既有文件（0001–0012）；本次只加核对不改迁移。
- **理由**：handoff §八 红线；迁移 0010 已应用，现状保留。
- **确认**：handoff §八。

### D6：不做功能级冒烟自动化
- **决策**：不做功能冒烟自动化（功能冒烟仍靠人工）。
- **理由**：handoff §二「明确不做」；#72 开放项。
- **确认**：handoff §二。

### F1 补强：scp 模式镜像核对不退化 —— CI 传构建镜像 ID
- **决策**：scp 应急模式的期望镜像 ID 由 **CI 构建步捕获**（`docker image inspect ... --format '{{.Id}}'` → step output），经 ssh 脚本作为 verify 第一参数传入；不再「服务器 load 后读 `:latest`」。
- **理由**：评审发现「load 到旧镜像 / 重跑旧 workflow」时，服务器读 `:latest` 的镜像核对会形式性通过（绿但旧码）——与本票要抓的信号同类；CI 侧捕获彻底堵死。
- **确认**：用户确认补强（2026-08-31，评审意见书 F1/Q3 采纳）。
