## 目标

用户在移动端输入搜索词，能找到标题或正文含该词的**帖子**，结果按相关性直觉排序、可分页，点入直达帖子详情。本票是「第二里程碑 · 社区功能完善」第一批（issue #1 决策 41）。

**范围相对票面的收缩**：票面「目标」与「验收线」含**评论检索**，用户在 D2 选择砍掉（评论搜索另票）。票面回写见 X11，已执行。

## 1. 票面开放决策定案（D1–D9）

### D1 中文检索技术路线 = 纯 `ILIKE` 子串匹配（多词按空白切分后 AND 组合）

- **问题**: `pg_trgm` 三元组模糊 / `to_tsvector` 内置分词 / 纯 `ILIKE` 全扫 / 引外部依赖？
- **选项**: A 纯 `ILIKE`（零迁移零扩展）；B `ILIKE` + `pg_trgm` GIN 索引；C `to_tsvector('simple')` + GIN；D 引外部中文分词（zhparser/pg_jieba）；E 外部搜索引擎。
- **决定**: **A**。
- **理由**（全部为本会话在 `postgres:16-alpine` 同镜像一次性容器内的实测，见设计文档 §2）:
  - **C 在中文上是坏的，不是质量差**：`to_tsvector('simple','AI 智联论坛 全文搜索 测试')` → `'ai':1 '智联论坛':2 '全文搜索':3 '测试':4`，一整串中文只按空白切成**一个** token；查 `智联论坛` 命中，查 `论坛` **不命中**。真实用户输入"论坛"搜"智联论坛"召回 0。
  - **D 不成立**：镜像内 `zhparser` / `pg_jieba` / `rum` / `pg_bigm` **均不存在**（票面约束复验为真）。
  - **B 无收益**：建了两个 `gin_trgm_ops` 索引后，即便 `enable_seqscan=off`，面对真实查询形态（`WHERE title ILIKE … ORDER BY id DESC LIMIT 20`）规划器**仍选 PK 反向索引 + Filter，完全不走 trigram 索引**；且 `ILIKE` 走 trigram 时**只加速不改召回**，模糊能力（`similarity`）才是会变召回的部分，而它在中文上是噪声（`similarity('全文搜索引擎','全文搜索')=0.5`、`word_similarity('论坛','AI 智联论坛 第3期')=0.333`）。
  - **A 是唯一零迁移路线**，对"迁移失败 → 容器 `os.Exit(1)` → 部署自动回退"（issue #1 决策 35 事故）**免疫**。
- **不选 B 的附加代价**: `CREATE EXTENSION` 只能进迁移，一旦该迁移在线上失败即整站发版失败；而 26 帖规模下它换不来任何可测收益。

### D2 搜索对象 = 仅帖子（标题 + 正文）；评论搜索移出本票

- **问题**: 帖子 / 评论 首版是否都要（票面 in 范围写两者，明确标注"可砍"）。
- **选项**: A 仅帖子；B 帖子 + 评论（分 tab）；C 帖子 + 评论 + 话题/标签名混排。
- **决定**: **A**。
- **理由**: 用户裁决——"没有人会专门去搜一个评论"。设计方此前以"评论是用户最常找的东西"给 B 加权，**该断言无任何数据支撑，已由用户质疑后撤销**（线上仅 26 帖、未接任何分析），故 B 不保留加权理由。
- **连带后果（已确认，不静默吞掉）**:
  1. 票面「目标」中"评论正文的关键词检索"与"评论命中应能定位到该评论"失效 → 票面已回写（X11）。
  2. X 决策原候选「评论命中落地跳 `/post/:id?c=<commentId>` 复用 `revealComment` 锚点」**不进入本票**。
  3. D5 原子问「父帖已删但评论未删的孤儿评论如何处置」**失去前提**（无评论命中）。
  4. 评论搜索建议作为「社区功能完善」后续候选挂账，由**统筹方**登记 issue #1 Roadmap（本会话无权限亦未越权）。
- **不选 C**: 标签已有 `/tag/:name` 落地页、话题有话题列表页，搜索里重复它们属扩大范围。

### D3 排序口径 = 标题命中优先 → `created_at DESC`；`q` 非空时跳过 `is_pinned DESC`

- **问题**: 时间倒序 / 复用 #61 热度打分 / 相关性优先；三者是否给分段切换。
- **选项**: A 与 Feed 完全同序（含置顶优先，后端零新分支）；B 标题命中优先 + 时间倒序；C 复用 #61 热度；D 给「时间/热度」分段切换。
- **决定**: **B**。用户明确接受"为搜索在排序构造里加一个分支"这一额外复杂度。
- **理由**: C 有可核缺陷——#61 热度是 **7 天窗口**内 `赞×1+评论×3`（`gorm_repo.go:107-120`，窗口条件 `:112`），搜索三个月前的内容时**所有结果得分同为 0**，实际退化成 `created_at` 序，却多背两个预聚合 LEFT JOIN。D 的成本（前端 tab 状态 + 后端 `sort` 参数 + 两套排序测试）在 26 帖规模上换不来收益。
- **实现要点**: 搜索态排序 `ORDER BY (title ILIKE $term) DESC, created_at DESC`；非搜索态排序**逐字节不变**（含 `is_pinned DESC`）。多词时"标题命中"定义为**标题包含全部词**。

### D4 登录墙 = 游客可搜（挂 `reads`/`OptionalAuth`）+ 后端最小 2 字符校验

- **问题**: 游客可搜？套用 IA「内容开放浏览、操作触发登录」时搜索属读还是属操作。
- **选项**: A 游客可搜；B 必须登录；C 游客可搜 + 后端校验 + 改 `web.conf` 加按 IP 限流 zone。
- **决定**: **A**，并采纳 C 中"后端最小查询长度"那一半（`≥2` 字符），**不采纳**改 `web.conf` 那一半。
- **理由**: 游客今天已能读帖子列表/详情/评论树（`router.go:134-141` 走 `OptionalAuth`，`handler/content.go:45-52` 游客 `viewerID=0`），只有"关注 tab"要求登录（`content/service.go:639-641`）→ 搜索属读。改 `web.conf` 要碰 nginx reload 与 bind-mount 坑（SOP §11），属本票范围外；**"搜索端点无独立限流"已登记为已知风险**（设计文档 §9），若日后要限流应另立运维票。

### D5 治理交互 = 与全站现状完全一致，不为搜索新增任何治理过滤

- **问题**: 软删内容、被封号作者的内容是否出现在结果；命中已删帖的占位策略。
- **决定**:
  - **软删帖不召回**——沿用 GORM 默认 scope（`gorm_repo.go:99` 注释所述），与 Feed/标签页同一口径；搜索态与非搜索态**必须同源**，否则同一列表接口出现两套治理规则。**不为搜索引入软删帖占位**（占位属既有 IA 议题，另票）。
  - **封号/已注销作者的内容照常召回**，作者位显示"已注销"。**理由**：`ListPosts` 今天**根本没有作者状态谓词**（`content/service.go:977-979` 只在作者查不到时降级显示），若搜索单独过滤封禁内容，会造成"同一个词搜索结果比列表页干净"的不一致；真正的"封禁内容全站下沉"应另立治理票。
- **票面子问"命中已删帖的占位策略"的答复**: 无占位——`ILIKE` 查询天然带 `deleted_at IS NULL`，删帖既不出现在 Feed，也不出现在搜索结果（两者同一函数）。

### D6 接口形态 = 复用 `GET /api/v1/posts?q=`，不新建搜索端点

- **问题**: `GET /api/v1/search?type=post|comment` 单端点 vs 分端点；读模型挂 `content` 包还是新抽象；跨包如何不破坏包边界。
- **选项**: A `/posts?q=`（给 `PostQuery`/`ListFeedQuery` 加一个字段）；B 新端点 `/search?q=`（返回体与 `/posts` 同构）；C 票面原样 `/search?type=post&q=`。
- **决定**: **A**。
- **理由（深模块接口三问 + 删除测试）**: A 的方法数增量 0、参数增量 1 个字段、复杂度全藏进 `gorm_repo` 的一行 `Where`；B 多出一个与 `/posts` **完全同构**的端点，删掉它复杂度不消失（前端换个 URL 而已）→ 浅接口重复；C 的 `type` 参数在 D2=A 之后只剩一个取值，是给不存在的多功能预埋位。
- **项目内同形先例**: #54 标签过滤即"专用页复用同一列表接口"——`PostCard.vue:38-44` chip → 路由 `/tag/:name` → `TagDetail.vue` → `api.listPosts({tag})` → `/posts?tag=` → `ListFeedQuery.Tag` → `gorm_repo.go:100` 子查询。搜索照抄该链路，`handler/content.go` 里 `if v := c.Query("q")` 与既有 `tag` 分支同构。
- **已确认代价**: 将来真要搜评论时，`/posts` 返回评论是语义错位，那一票必须另开端点（接口演进的账记在未来）；`backend/content/README.md` 须补一段 `q` 的语义（多词 AND、不区分大小写、按字面匹配、不做相关性打分、`total` 仅搜索态出现）。
- **包边界**: 搜索**不跨包**（D2=A 后只搜帖子，不需要作者名检索），因此不触发"跨包调用经接口"的装配改动；`main.go` 与 `router.go` 均**零改动**（`/posts` 已在 `reads` 组）。

### D7 迁移 = **零迁移**（不建扩展、不建索引、不建表）

- **问题**: 是否为搜索新增迁移。
- **决定**: **否**。
- **理由**: D1 的技术路线不需要扩展也不需要索引；本仓库既有 13 个迁移文件全部是纯 DDL，**没有任何 `CREATE EXTENSION` / `DO $$` / `CONCURRENTLY` 先例**，本票若加即是第一个非纯 DDL 文件，而 `migrate.go:43` 每迁移包一个事务 + `:65` 按 `;` 朴素切分语句 ⇒ 迁移内既不能用 `CREATE INDEX CONCURRENTLY`，也不能写含分号的函数体。**收益为零、风险为整站发版**，故不做。
- **核对点**: 上线后 `schema_migrations` 应**仍停在 `0012_notify_type_mention.sql`**（`version` 列存文件名，非整数）。若出现新行即为实现跑偏。

### D8 前端 = 首页「入口壳」→ L2 结果页 `/search?q=`，输入只发生在结果页

- **问题**: 搜索入口位置（IA v2 曾取消占位框，须重新定）、结果页路由与"两级扁平层级/Tab 隐藏"规则如何套用。
- **选项**: A 首页 `SegTabs` 上方入口壳，点它跳 `/search`，输入在结果页；B 首页顶部可输入框 + 回车跳 `/search?q=`；C 全局 nav-bar 右上图标；D 只建路由，入口藏在「我的」/板块页。
- **决定**: **A**。
- **理由**: A 有项目内可照抄的同形先例（见 D6 标签链路）；B 要在 L1 承载输入态并重复一套结果页逻辑，而项目**没有 debounce 工具**（只有 `Write.vue:27-40` 的内联 `setTimeout` 先例）；C 给全站 `App.vue:37-44` 的 nav-bar 开"使用 `#right` 槽"的先例（今天**全站无一处使用**），且移动端右上角比顶部条更难触达；D 发现性最差。
- **结果页层级**: `/search` 为 **L2**（隐藏 Tab、全屏 push 带返回，符合 `info-architecture.md:60` D3 层级与 `:136` §5.1 显隐规则）；URL **hash 路由带 `q` 查询参数**——"返回保留查询词"这条验收线靠 `q` 在 URL 里自然成立，项目今天**没有 `scrollBehavior`/`keep-alive`/查询态保持机制**（`router/index.ts` 无相关代码），**滚动位置恢复不在本票范围**。
- **IA 文档回写**: 落地时须改写 `docs/ux/info-architecture.md` 中"取消搜索占位框"的三处条目（`:5` 定稿裁决、`:58` D1、`:199` §7、`:228` §9 修订记录），登记为实装条目（票面验收线已要求）。

### D9 存量数据 = 无回填、无索引窗口期

- **问题**: 是否回填、是否需在建索引窗口期注意什么。
- **决定**: 两者皆**无**——D7 零迁移的直接推论。查询直接打在既有 `content.posts.title/content` 列上，无派生数据、无一致性窗口。

## 2. 会话新开前沿定案（X1–X11，票面未列但不可静默假设）

### X1 通配符按字面匹配 + 输入约束（≥2、≤64 字符、≤4 词）

- **问题**: `ILIKE` 中 `%`/`_` 是通配符、`\` 是转义符，用户输入 `50%` 会变成"以 50 开头"。
- **选项**: A Go 侧转义（`\`→`\\`、`%`→`\%`、`_`→`\_`）后按字面匹配；B 保留通配符当高级功能；C 直接拒绝含 `%`/`_` 的输入。
- **决定**: **A**。约束：`strings.TrimSpace` 后 **长度 ≥2 且 ≤64**，按空白切词，**词数上限 4**；违反即返回参数错误（状态码复用现有 `respondContentError` 映射体系，实现时先核对既有 4xx 惯例，不新造）。**超出 4 词一律拒绝、不静默截断**——本条最终定案见设计文档 §6-3（此处"取前 4 词"的表述已在该节纠正）。
- **理由**: B 给社团论坛装一个没人要的查询语言，且 `_` 在代码/链接正文里大量出现会意外放大召回；C 让"搜 `a_b`"变成不可能。A 成本 ≈6 行 Go + 3 条单测。

### X2 大小写 = 不区分（继承 `ILIKE` 语义），且前端高亮必须与之对齐

- **决定**: 不区分大小写。这是 `ILIKE` 的既有语义，非额外功能。
- **强制项**: ①集成测试须钉**一条英文大小写用例**（否则票面验收线"大小写策略有明确结论"无法落地）；②前端高亮定位两侧统一 `toLowerCase()`（X4），否则出现"后端命中、前端不高亮"。
- **已知限制**: 带变音符号的拉丁字母（如 `é`/`e`）两侧仍可能不一致，**接受并登记**，不为它引归一化依赖（`unaccent` 虽在镜像内可用，但引入即破坏 D7 零迁移）。

### X3 繁简转换 = 明确不做

- **决定**: 不做，写入「明确不做」清单并登记未来触发条件。
- **理由（实测）**: PG 无内置汉字繁简能力；镜像内只有 `unaccent 1.1`（只处理重音，不管汉字）、`pg_trgm 1.6`、`btree_gin 1.3`；`zhparser`/`pg_jieba` 不存在。真做须引映射表或第三方依赖，与 D1 的裁决方向相反。

### X4 命中词高亮 = 前端纯函数返回分段数组，**禁 `v-html`**

- **问题**: 高亮（用户从"明确不做"清单里点名挪回 in 的唯一一项）走哪条渲染路径。
- **选项**: A 新增 `frontend/src/utils/highlight.ts`，输入 `(text, terms[])` 输出 `[{text, hit}]`，模板 `v-for` + `<mark>`；B 后端拼 `<mark>` 前端 `v-html`；C 前端拼 HTML 串再 `v-html`。
- **决定**: **A**。
- **理由**: Vue 对文本节点自动转义 → **零新增 XSS 面**，且是可直接单测的纯函数。B 把 markup 混进后端读模型（`PostView` 要加字段或改现有字段语义）并永久背上"这字段是 HTML"的约定；C 把转义顺序变成手写地雷（`md.ts:7-12` 的 `escapeHTML` 存在即说明这条线踩过坑）。

### X5 高亮载体 = 给 `PostCard.vue` 加**可选** prop，不新建搜索专用卡

- **决定**: `terms?: string[]`（命中词，触发高亮）+ 复用同一张卡；不传时行为**逐字节不变**。
- **理由（删除测试）**: 新建 `SearchResultCard.vue` 会留下两份卡片模板与样式，日后改一次卡片要记得改两处；删掉这份重复，复杂度不会消失（会变成"两份卡片悄悄长得不一样"）。
- **已确认代价**: `PostCard.vue` 多两个分支，其单测须多盖对应路径。

### X6 命中上下文片段 = 前端从 `PostView` 全量正文算，后端不加字段

- **决定**: 前端对 `plainText(post.content)` 定位**最先出现**的命中词，截取前后各约 40 字，两端加 `…`；若正文内无命中（即仅标题命中）则**回落到现有的正文前两行截断**（与 Feed 表现一致）。
- **理由**: `PostView` 今天已把**全量 markdown 正文**发给前端（`content/service.go:23-44`；`PostCard.vue:47` 用 `plainText()` + CSS 两行截断），前端算片段**零后端改动**。后端返 `matched_snippet` 需 markdown 剥离，而现成剥离器 `stripMarkdownForMatching` 是**包内私有**（`content/tags.go:34-43`），导出即扩大接口面，且该文件 `:8-9` 有明文纪律"Go/TS 两套正则改一侧须改另一侧"——后端再算一份等于往这个双侧同步负担里塞第三处。

### X7 结果总条数 = 仅 `q` 非空时 COUNT，响应新增可选 `total`

- **决定**: 搜索态额外跑一次 `COUNT(*)`，`/posts` 响应在 `q` 非空时多一个 `total` 字段；结果页顶部显示"找到 N 条结果"，`N=0` 时用 `Empty.vue` 显示"没有找到「<词>」的相关帖子"。Feed/标签页/首页**完全不受影响**。
- **理由（实测）**: `/posts` 当前响应是 `gin.H{"items","page","page_size"}`（`handler/content.go`），**全仓库无 `total` 字段**（grep 零命中），无限滚动今天不知道总数。与"不显示条数"相比，唯一实质差别是用户能区分"真的没结果"与"请求失败了"。`total` **不参与翻页逻辑**，分页仍靠 `items` 到底。26 行表上 `COUNT(*)` 瞬时，且不受 D1 那条"trigram 索引不被使用"发现的影响。
