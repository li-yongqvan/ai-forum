# Ubiquitous Language

> ai-forum 项目术语表（提取自 2026-08-19 ~ 08-24 统筹会话）。领域专家/参与会话的 agent 统一用语。

## 业务域（论坛社区）

| Term | Definition | Aliases to avoid |
|---|---|---|
| **帖子** | 用户发布的内容单元（标题 + Markdown 正文 + 可选图片） | 内容、文章 |
| **评论** | 对帖子或其他评论的回复（树状嵌套 = 楼中楼） | 回复（回复是动作） |
| **楼中楼** | 评论的树状嵌套结构（父评论 + 子评论）；展示层默认只显一级 +「展开 N 条回复」 | 嵌套评论、回复树 |
| **板块** | 帖子的顶级分类（如「闲聊灌水」） | 分区 |
| **话题** | 板块下的子组织单位，发帖时可选 | 标签、分类、主题 |
| **标签（#hashtag）** | 帖子正文内 `#关键词` 内嵌的可点击维度，点入聚合页（#54 开发中） | tag、话题、主题 |
| **点赞** | 对帖子的赞同（♥） | 赞、喜欢 |
| **收藏** | 保存帖子稍后查看（☆），含「我的收藏」列表 | 书签、存 |
| **关注** | 订阅对象（用户/板块/话题）的新帖，含「我的关注」列表 | 订阅、follow |
| **通知** | 系统推送的互动/治理消息（如「X 关注了你」、`report_result`） | 消息（私信语义冲突） |
| **私信** | 用户间的直接消息（messages 表，未上线，tab 占位） | 站内信、消息 |
| **举报** | 用户提交违规内容给管理员处理（六枚举原因 + 备注） | 投诉、report |
| **举报人** | 发起举报的用户（当前是 `report_result` 唯一接收方） | 报告人、submitter |
| **被举报人** | 被举报内容的作者（当前收不到处理通知，#53 补触达） | 被告、target |
| **治理** | 举报 → 处理 → 封禁 → 审计 → 结果通知 的闭环 | 管理、moderation |
| **封禁** | 管理员禁用账号（登录拒 + 写操作拦截，admin-only） | 拉黑、ban |
| **审计记录** | 治理动作的 append-only 留痕（`moderation_actions`） | 日志、审计日志 |

## 协作域（wayfinder 机制）

| Term | Definition | Aliases to avoid |
|---|---|---|
| **地图** | GitHub issue #1，项目唯一状态机（Destination/Notes/决策日志/Roadmap/开放项） | 进度、文档 |
| **ticket** | GitHub issue，一个功能/修复的任务卡（child of 地图，带 `wayfinder:*` 标签） | issue、票、需求 |
| **PR** | GitHub Pull Request，代码合并请求（与 issue 共用编号空间） | merge request |
| **handoff** | 给零上下文下一会话的自包含交接文档（`docs/handoffs/`，非持久化工作底稿） | 交接、转交 |
| **grilling** | 实现前与用户逐项确认开放决策（SOP §3 第 0 步，HITL） | 评审、需求澄清 |
| **评审** | 独立 plan-review 对方案/设计文档的批判性审查（产出意见书） | grilling、code review |
| **SOP** | 操作手册 `docs/workflow.md`（功能开发标准流程） | 流程文档、指南 |
| **HITL 红线** | 需用户明确授权的动作：合并 PR / 删生产数据 / 关闭 issue | 审核、批准 |
| **统筹方** | 规划协调会话（建票 / 出 handoff / 更新地图 / 收口） | 协调者、管理员 |
| **收口** | ticket 完成后的关闭 + 记录（关 issue + 地图决策日志追加） | 收尾、完结 |
| **worktree** | git worktree 隔离并行会话工作区（防串分支） | 分支、工作区 |
| **发版** | CI 构建 → 部署 → 服务器验证 的上线流程（现状 ~18min） | 部署、release |

## Relationships

- 一个**帖子** 属于一个**板块**，可选挂一个**话题**；可含多个**标签（#hashtag）**。
- 一个**评论** 属于一个**帖子** 或另一条**评论**（形成**楼中楼**）。
- 一条**举报** 由**举报人** 发起，指向**被举报人** 的内容；经**治理** 产生**审计记录** 和**通知**。
- 每个 **ticket** 是**地图** 的 child；每张 **handoff** 对应一个 **ticket**；ticket 完成 → **收口**（关 ticket + 地图决策日志记**里程碑**）。
- **地图** 由 **统筹方** 独占更新（并行会话不 edit issue #1）。

## Example dialogue

> **Dev:** "#54 做**标签**，会不会和发帖时选的**话题**重复？"
> **领域专家:** "不重复——**话题** 是发帖时选的组织单位（板块下），**标签** 是正文里 `#关键词` 内嵌的轻量维度，点进**聚合页**。两者互补，不冲突。"
> **Dev:** "那**举报**后，**被举报人** 会收到什么？"
> **领域专家:** "现在 `report_result` 只发**举报人**；#53 要补**被举报人** 触达——这是对 D33-2 的**策略变更**，得先 **grilling** 确认是两边都发还是改发。"
> **Dev:** "合并前我要跑什么？"
> **领域专家:** "**SOP** 流程：测试全绿 → PR → **用户授权**（HITL 红线）→ 合并 → **发版** → 服务器验证；完成后**收口**，回报**统筹方** 更新**地图**，别自己 edit #1。"

## Flagged ambiguities

- **"话题" vs "标签"**：二者都组织内容、中文易混。**话题** = 发帖时选择的组织单位；**标签（#hashtag）** = 正文内嵌的可点击维度。#54 grilling 决策 4 必须确认互补关系。
- **"通知" vs "私信" vs "消息"**：`notifications`（系统互动）vs `messages`（用户私信）——"消息"一词两义，规范：系统侧用**通知**，用户间用**私信**。
- **"关注" 的三种对象**：用户 / 板块 / 话题 都叫"关注"——动词相同、对象不同，上下文须说全（如"关注用户"）。
- **编号空间共享**：GitHub 中 PR 与 issue **共用编号**（曾把 PR #27 误当 ticket）。引用必须带类型前缀：`issue #N` / `PR #N`（SOP §8 引用规范）。
- **"grilling" vs "评审" vs "code-review"**：grilling = 实现前与用户定决策（HITL）；评审 = plan-review 审查方案/设计文档；code-review = 合并前代码审查。三个不同过程，勿混用。
- **"收口 / 收尾 / 完结"**：同指 ticket 完成后的关闭+记录动作，规范为**收口**。
- **"ticket" vs "issue"**：wayfinder 语境规范用 **ticket**（任务卡语义）；issue 是 GitHub 底层类型。
